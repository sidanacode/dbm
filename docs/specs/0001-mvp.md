# Specification 0001: DBM coordinator MVP

Status: Accepted for implementation

Date: 30 September 2026

## 1. Purpose

DBM detects cross-branch schema conflicts before Alembic migrations are finalized. It stores proposed schema-change intent, compares active work deterministically, and gives coding agents structured facts they can explain to developers.

## 2. Product boundary

DBM owns proposed and in-flight schema work. The default Git branch owns accepted migration history. Connected databases, when added later, report deployed state and drift.

Version 0.1 does not yet execute application migrations, connect to production databases, edit Git branches, or approve semantic reinterpretations. This is an implementation milestone, not the final product boundary: specification 0004 adds DBM-controlled migration deployment.

## 3. Actors

- A developer changes application models and approves semantic decisions.
- A local CLI or coding agent derives and submits intent.
- The coordinator stores team-wide state and performs deterministic checks.
- Alembic generates migrations during this milestone. In the complete product, DBM invokes Alembic inside an isolated runner as specified by specification 0004.
- Git determines accepted order through merges to the configured default branch.

## 4. Functional requirements

### REQ-PROTOCOL-001: versioned intent

Every intent must declare protocol version `1`, project identity, branch, commit SHA, base Alembic heads, migration-graph digest, and one or more schema operations.

### REQ-PROTOCOL-002: operation support

Protocol version 1 must support:

- add table and drop table;
- add, drop, alter, and rename column;
- add and drop index;
- add and drop foreign key.

### REQ-STATE-001: canonical project state

A project stores its default branch, accepted Alembic heads, and accepted migration-graph digest. Updating this state creates an audit event.

### REQ-INTENT-001: intent lifecycle

An intent can move through submitted, approved, leased, merged, cancelled, or superseded states. The API must reject invalid transitions.

### REQ-CHECK-001: deterministic outcomes

Checking an intent must return one primary outcome:

- `safe` when no finding applies;
- `stale` when its graph digest differs from accepted project state without a higher-priority finding;
- `dependent` when it requires an object proposed by another active intent;
- `conflict` when operations cannot safely coexist as written.

Outcome priority is conflict, dependent, stale, then safe. The response must retain all findings.

### REQ-CHECK-002: required conflicts

The engine must detect:

- duplicate creation of the same table, column, index, or foreign key;
- dropping a table while another intent changes an object in that table;
- dropping an object another intent alters, renames, or creates;
- concurrent alteration of the same column;
- renaming a column another intent references;
- incompatible concurrent renames of the same column;
- conflicting foreign-key or index operations with the same identity.

### REQ-CHECK-003: dependencies

Adding a foreign key that references a table created by another active intent must produce a dependency finding containing the related intent ID.

### REQ-APPROVAL-001: approval gate

Only an intent whose latest check has no conflict may be approved. Approval never means that an AI interpretation has been accepted implicitly; the caller represents the developer's decision.

### REQ-LEASE-001: finalization lease

An approved intent may acquire a short-lived project lease only when its base graph digest matches accepted project state and no unexpired project lease exists. A lease does not allocate a permanent Alembic revision ID.

### REQ-AUDIT-001: audit history

Project creation, state updates, intent submission, checks, approvals, cancellations, lease acquisition, and lease release must create immutable audit events.

### REQ-API-001: HTTP API

The coordinator must expose versioned JSON endpoints for project creation and state, intent submission and listing, checks, approval, cancellation, lease acquisition, and release.

### REQ-AUTH-001: optional shared token

When `DBM_API_TOKEN` is set, all `/v1` endpoints must require the matching bearer token. Health checks remain public.

### REQ-CLI-001: local CLI

The `dbm` CLI must read `.dbm.toml`, inspect local Git and Alembic state, and call the coordinator for the supported intent lifecycle.

### REQ-MCP-001: MCP tools

The MCP server must expose structured tools for project state, submitting and listing intents, checking, approving, cancelling, acquiring a lease, and releasing a lease.

### REQ-MCP-002: MCP container image

The MCP server must run as a non-root Docker container using Streamable HTTP. The image must accept coordinator URL, API token, bind host, bind port, and MCP path through configuration. Tagged releases must be publishable to GitHub Container Registry.

## 5. Non-functional requirements

### REQ-NFR-001: deterministic core

The conflict engine must be a pure function independent of HTTP, persistence, and LLM services.

### REQ-NFR-002: database support

The deployed coordinator supports PostgreSQL. Automated tests may use SQLite without changing application behavior.

### REQ-NFR-003: machine-readable failures

HTTP errors and conflict findings must include stable codes suitable for CLI and agent handling.

### REQ-NFR-004: local onboarding

A contributor must be able to install, test, and run the coordinator using `uv` and Docker Compose instructions in the repository.

### REQ-NFR-005: open-source workflow

Development must use topic branches and pull requests against `main`. The repository must include an Apache-2.0 license, contribution instructions, a code of conduct, a security reporting policy, issue templates, and automated quality checks.

## 7. Acceptance scenarios

### AC-001: rename conflict

Given an active intent that renames `users.name` to `users.full_name`, checking another intent that alters `users.name` returns `conflict`, code `object_renamed`, the related intent ID, and the new object identity.

### AC-002: independent changes

Given an active intent that adds `users.phone`, checking an intent that adds `orders.reference` returns `safe` when its base matches project state.

### AC-003: stale but non-overlapping

Given a non-overlapping intent whose graph digest differs from project state, checking it returns `stale` rather than `conflict`.

### AC-004: dependency

Given an active intent that creates `organizations`, checking an intent that adds a foreign key from `users.organization_id` to `organizations.id` returns `dependent` and identifies the first intent.

### AC-005: lease serialization

Given two approved intents on the accepted graph, only one can hold an unexpired project finalization lease at a time.

### AC-006: authentication

Given a configured API token, requests without the matching bearer token receive HTTP 401 while `/health` remains available.

### AC-007: MCP container

Given a configured coordinator URL, the MCP Docker image starts as a non-root process, exposes Streamable HTTP, and passes its health check.

## 8. Explicitly deferred

- database inspection and schema drift;
- production migration execution in version 0.1 (specified for a later milestone in specification 0004);
- GitHub or GitLab applications;
- automatic branch mutation or pull-request merging;
- dashboard UI;
- LLM API integration;
- frameworks other than Alembic;
- database engines other than PostgreSQL;
- deployment-safety linting and expand-contract planning.
